# План управления рисками

Для каждого риска — стратегия (снизить / принять / передать) и конкретные меры.
Помечено, что решается **техническими** (T) средствами, а что — **управленческими** (M).

## Архитектурные

| # | Меры | Тип |
|---|---|---|
| A1 | Чёткие bounded contexts по DDD; асинхронные контракты; запрет синхронных вызовов на критическом пути; fitness-функции на связность | T + M |
| A2 | Data contracts + Schema Registry; проверка совместимости схем в CI/CD; идемпотентные консьюмеры | T |
| A3 | Каталог данных (DataHub) как единая точка обнаружения; ревью продуктов данных; переиспользование вместо копий | T + M |
| A4 | Поэтапный план с датами вывода legacy; метрика «доля трафика мимо DWH/Camel»; sunset-критерии моста | M |
| A5 | Для строгой согласованности (платежи) — синхронные транзакции/saga внутри домена; eventual consistency только между доменами | T |

## Организационные

| # | Меры | Тип |
|---|---|---|
| O1 | Обучение, найм, внешние консультанты; пилот на 1–2 доменах для накопления экспертизы | M |
| O2 | Постепенный переход; демонстрация быстрых выгод (time-to-market) на пилоте | M |
| O3 | Назначить Data Product Owner на каждый домен; зафиксировать ответственность | M |
| O4 | Кросс-функциональные команды, закреплённые за доменом; не «арендовать» людей между доменами | M |
| O5 | Роадмап с измеримыми вехами по кварталам; регулярная отчётность бизнесу | M |

## Технологические

| # | Меры | Тип |
|---|---|---|
| T1 | RBAC/ABAC, шифрование, аудит, классификация чувствительных данных в каталоге; медкарты/снимки исключены из аналитики; провайдер с сертификацией 152-ФЗ | T |
| T2 | Открытые форматы (Iceberg, S3, Kafka) → вендоронезависимость; абстракция через IaC | T |
| T3 | IaC (Terraform), наблюдаемость (трейсинг/мониторинг), staging-среды, постепенный rollout | T |
| T4 | CDC + репликация со снапшотами; параллельный прогон legacy и нового; сверка данных; rollback по снапшотам Iceberg | T |
| T5 | Горизонтальное масштабирование Kafka/движка; партиционирование; нагрузочное тестирование | T |
| T6 | DLQ, at-least-once + идемпотентность, ретраи, алерты на лаг консьюмеров | T |

## Сводная стратегия

- **Снижать вероятность и влияние (приоритет):** A4, O1, A1, A5, O3, O5, T6.
- **Контролировать (высокое влияние, низкая вероятность):** T1, T4 — жёсткие технические барьеры и регулярный аудит.
- **Принять и мониторить:** T2, T3, T5 — отслеживаем метрики, реагируем по порогам.
- Каждое архитектурное изменение фиксируется в ADR; риск-карта пересматривается ежеквартально вместе с роадмапом.
