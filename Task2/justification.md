# Обоснование событийного подхода (vs Camel/DWH)

## Проблемы текущего состояния
- **ESB Camel** — центр синхронных интеграций: точечные связи, сильная связность,
  отказ одного звена влияет на остальные, рост связей O(n²).
- **DWH (SQL Server 2008)** — единая точка с бизнес-логикой и «бутылочное горлышко»
  в виде команды хранилища; любое новое направление требует правок в DWH.
- **Batch-отчётность** — формирование сложных отчётов занимает часы; нет near-real-time.
- Плохая масштабируемость при подключении новых доменов (фарма, электроника, регионы).

## Что даёт переход на события

| Критерий | Camel + DWH (сейчас) | Событийная интеграция (цель) |
|---|---|---|
| Связность | Жёсткая, синхронная | Слабая, асинхронная (pub/sub) |
| Масштабирование | Через центральную команду/DWH | Независимо по доменам; партиционирование Kafka |
| Подключение нового домена | Правки в DWH/Camel | Подписка на события + свой продукт данных |
| Скорость реакции | Batch, часы | Near-real-time потоки |
| Отказоустойчивость | Каскадные сбои | Изоляция, ретраи, DLQ, буферизация |
| Time-to-market | Низкий (узкое место) | Высокий (автономия доменов) |
| Эволюция контрактов | Неявная, ломкая | Schema Registry + версии, проверка совместимости |

## Конкретные выгоды для «Будущего 2.0»
- **Гибкость:** домены развиваются независимо; новые бизнес-направления интегрируются
  через подписку на существующие события без изменения чужого кода.
- **Масштабируемость:** Kafka масштабируется горизонтально; рост источников и событий
  (долгосрочная цель) поглощается партиционированием.
- **Скорость реакции:** переход от batch к near-real-time витринам — отчёты строятся
  на потоках, а не за часы.
- **Снятие «бутылочного горлышка»:** бизнес-логика уходит из DWH в домены; команда
  хранилища перестаёт быть единственным владельцем всех данных.
- **Безопасная миграция:** Camel и DWH остаются как ACL-мосты, постепенно выводятся;
  событийная модель строится параллельно без «большого взрыва».

## Цена решения (трезво)
- Рост сложности инфраструктуры и требований к компетенциям (Kafka, Iceberg, потоки).
- Eventual consistency между доменами → для строгой согласованности (платежи) транзакции/saga
  остаются внутри домена.
- Нужна дисциплина контрактов и governance, иначе событийный «спагетти» вместо порядка.

**Вывод:** событийная платформа напрямую закрывает боли компании (time-to-market,
масштабирование, near-real-time), а Camel/DWH разумно сохранить как временные мосты совместимости.
